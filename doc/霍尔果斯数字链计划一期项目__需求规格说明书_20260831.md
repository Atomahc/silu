# 引言

## 编写目的

本文档旨在为霍尔果斯“数字链计划”一期项目提供完整、一致且可验证的需求基线，作为系统设计、开发实现、测试验证与最终验收的共同依据。本需求规格说明书（SRS）基于招标文件中的功能、技术与实施要求进行系统化梳理与规范化表述，确保内容完整、逻辑严密、术语准确，满足GB/T 8567—2006《计算机软件文档编制规范》和GB/T 9385—2008《软件需求规格说明规范》的要求。

## 项目背景

霍尔果斯“数字链计划”一期项目是响应国家“数字中国”战略及自治区“数据要素×”行动的重要举措，立足于霍尔果斯作为“一带一路”跨境合作核心枢纽的特殊定位，致力于破解区域数据孤岛、服务碎片化等发展瓶颈。通过构建“一中枢、一门户”的城市级数字底座，推动全域数据贯通、服务集约共享与决策智能支撑，形成可复制、可推广的“霍尔果斯模式”，为边疆地区数字化治理现代化提供样板示范。

# 总体描述

## 产品愿景

本项目旨在构建“一中枢、一门户”的城市级数字底座。“数据协同调用中枢”负责实现全域数据的采集、治理、开发与共享，打通数据壁垒；“数字霍尔果斯·全域统一综合服务门户”则作为对外服务的统一入口，整合政务服务、企业服务与便民事项。最终目标是实现数据贯通、服务集约、决策智能，打造可复制的“霍尔果斯模式”，赋能区域经济社会高质量发展。

## 用户特征

系统主要服务于三类用户群体，其权限与使用场景存在显著差异：

• **政府工作人员**：包括普通职员与各级领导。普通职员主要使用业务办理、数据查询等功能；领导层侧重于通过数据驾驶舱进行宏观态势感知与决策支持。

• **企业用户**：主要为在霍尔果斯注册或开展业务的企业法人，关注政务服务专区、口岸服务专区、就业务服务专区等功能，以提升办事效率与商业便利性。

• **普通居民/境外人员**：涵盖本地居民及往来霍尔果斯的外籍人士。该群体主要使用便民服务专区、云上法务专区及境外人员入境便利化专区，获取生活、法律与通关相关服务。

## 假定的约束

### 技术假定

需提供系统运行所需的服务器资源和网络资源，需要支持电子政务外网和互联网区域之间有可用的网闸进行通讯。

### 业务假定

数字名片和数据驾驶舱面向的用户是政府工作人员

数字名片和数据驾驶舱以各委办局提交到中台的数据为分析原料，具体指标或趋势的分析需要根据具体数据调整。

门户支撑平台需要使用微信，支付宝和新疆政务服务网单点登录，需要甲方申请微信开放平台，支付宝开放平台和新疆政务服务网单点登录的账号信息。

数据回流需要甲方协助向上级部门和单位提交数据回流申请，行政审批通过后由乙方进行技术实现。

## 运行环境

### 客户端环境

• **浏览器**：支持Chrome、Firefox、Safari最新版及其前一个版本。

• **移动端**：支持iOS 15及以上版本、Android 10及以上版本的操作系统微信小程序运行环境。

• **专用终端**：支持部署于公路口岸、旅检大厅等地的自助服务终端设备。

### 服务器端环境

• **操作系统**：麒麟OS V10或更高版本。

• **数据库**：应用兼容Mysql，PostgreSql ，GaussDB 200、达梦数据库 DM8，等。

• **中间件**：支持东方通TongWeb V7，Tomcat等。

• **JDK**：最低支持Oracle JDK 1.8 或 OpenJDK 1.8 及以上版本。

## 假设与依赖

• 假设第三方API（如国家政务服务平台身份认证接口）能够稳定可用。

• 假设内部网络延迟不超过100ms，保障实时数据交换的时效性。

• 假设伊犁州平台及自治区一体化数据资源服务平台已开放数据回流通道，并能按约定格式提供数据。

## 设计约束

• 系统可采用Java，go，python等语言进行开发前端主要使用vue，react，html，css，js等技术进行开发。

• 系统整体架构与安全体系必须符合网络安全等级保护第三级（等保三级）要求<sup>[2](https://blog.csdn.net/heqinghua217/article/details/127921683)</sup>。

• 密码应用方案必须满足《GB/T 39786-2021》中规定的第三级密码应用基本要求，优先使用国密算法（SM2/SM3/SM4）。

## 门户服务平台

### 数字城市名片

数字城市名片是霍尔果斯“数字链计划”一期项目的对外展示窗口，以一幅可横向滚动、可点击探索的“数字城市长卷”为载体，呈现霍尔果斯从古丝绸之路驿站到现代化口岸城市的演进脉络。系统面向来访领导考察、招商推介、汇报演示、大屏展示等场景，承担“宏观态势一屏统览、城市形象一卷呈现”的定位。

系统采用“插画长卷叙事 + 6大分类指标分析”的双层结构：长卷负责视觉叙事与城市形象展示，指标浮层按招标要求的6大分类组织数据分析，两者通过场景-分类映射关系衔接。

## 门户支撑平台

支撑平台层是门户的底层共性能力集合，包含统一身份认证、统一用户档案、统一授权管理、内容管理系统、个性化门户、多终端适配及多语言适配等7个核心组件，为上层服务平台层的各类应用提供统一、标准化的支撑能力，确保门户服务的一致性、安全性与灵活性。

### 统一身份认证

霍尔果斯数字联计划由多个系统组成，来支撑市域社会治理现代化相关业务开展，因此需要对多个系统进行身份认证管理，实现市域社会治理工作人员系统登录一网通行。统一用户认证为霍尔果斯市市域社会治理现代化管理平台各系统提供统一的用户管理、权限管理、组织架构管理、身份认证及单点登录服务功能。

统一用户管理系统主要包含组织机构管理、用户及权限管理、统一登录认证服务、认证应用管理、访问控制管理、安全审计管理、统计分析功能及统一用户接口服务。

建立并管理全市统一的数字身份体系，为所有应用提供安全、便捷的登录认证服务。需具备包括但不限于用户库、身份证生命周期管理、多元身份同步、统一认证、多凭证支持、会话管理、单点登录协议与集成及统一权限管理等功能。

3\. 授权主体配置

定义了“谁”拥有该权限：

子用户：指定具体拥有该权限的用户（如 alice， bob）。

子角色：指定拥有该权限的角色（如 admin， editor）。属于这些角色的所有用户将自动继承该权限。

4\. 资源与操作配置

资源类型：用于资源的自定义分类（外部应用认证时通常可忽略）。

资源：描述需要强制权限控制的资源。可以是 URL（如/api/users）、文件名（如document.pdf）或资源标识符（如project:123）。

操作：描述对资源执行的动作。可以是 HTTP 方法（如GET，POST）、CRUD 操作（如read，write）或自定义动作（如view，edit）。

效果：定义策略的最终效果（如允许或拒绝）。

5\. 动态关联属性

当通过 API 获取用户对象时，系统会动态填充该用户的权限列表，其中包含以下关联属性：

Users：属于该权限的用户数组。

Roles：属于该权限的角色数组。

IsEnabled：标识该权限是否处于启用状态。

CreatedTime：权限的创建时间。

### 应用系统对接

#### 标准化接口

在统一权限模型与策略引擎支撑下，权限管理从“静态分配”升级为“动态决策”。应用系统通过对接身份认证、权限评估、资源注册、事件通知等标准化接口，即可无缝融入企业级授权体系，实现：

1\. 身份认证接口：

支持标准的 OAuth 2.0 和 OIDC 协议。应用可以通过标准的Authorization Code（授权码模式）、Client Credentials（客户端凭据模式）等多种 Grant Types 获取 Access Token 和 ID Token。支持通过 SDK 快速集成。

2\. 权限评估接口

提供了Enforce()API，允许应用传入请求上下文（如主体sub、资源obj、操作act等），实时获取“允许（Allow）”或“拒绝（Deny）”的授权决策。应用可以直接调用此接口进行网关级或业务级的二次校验。

3\. 批量权限查询接口

提供查询用户关联的角色和权限列表的接口（GetPermissionsAsync()获取权限列表）。如/authz/permissions?resources=menu1，menu2的批量布尔值结果。实现前端界面的批量菜单/按钮控制，或通过多次调用实现。

4\. 资源注册接口：

提供 RESTful 管理 API（如User/Org/App Management API和Role/Permission CRUD API），支持通过 OpenAPI 规范进行资源的增删改查。应用可以通过调用这些管理接口，将自身的受控资源（如 API 路径、数据对象）注册到平台中，并在配置权限策略（Permissions）时直接引用这些资源标识符。

5\. 权限变更通知：通过 Webhooks

实现 Webhooks 功能。当用户、角色或权限策略发生变更时，平台可以主动向配置好的 URL 发送通知。应用系统可以监听这些 Webhook 事件，从而及时更新本地缓存或触发重新鉴权，保持数据一致性。

6\. 审计日志上报接口：

实现完善的观测层（Audit Plane）。实现审计日志记录功能（如RecordMessage过滤器），支持结构化日志输出，能够完整记录主体、权限范围、工具、决策原因及追踪 ID 等审计字段。同时，它也支持与外部 SIEM 或可观测平台进行集成扩展，满足安全审计与策略优化的需求。

安全可控目标建立完善的身份认证和权限控制机制，确保用户数据安全。遵循国家网络安全等级保护要求，满足政务系统的安全合规要求。

### 集成模式

根据各被集成系统的技术架构和业务特点，采用不同的集成模式进行对接。集成模式包括接口调用集成、数据同步集成和门户融合集成三种类型。

接口调用集成通过HTTP/HTTPS协议进行接口调用，实现实时数据交互。适用于政务服务平台、企业服务系统等具有开放API能力的系统。

数据同步集成适用于老旧系统或无法提供实时API的系统，通过数据库层面的ETL工具进行批量数据同步。适用于历史数据迁移、定时数据汇总等场景。

门户融合集成适用于需要深度整合用户体验的系统，通过单点登录、页面嵌入等方式实现无缝衔接。适用于需要"一站式"办理的业务场景。

### 联调实施

#### 联调准备与规划阶段

在联调准备阶段，全面梳理霍尔果斯“数字链计划”一期项目所涉及的数据系统、接口及业务流程。组织跨部门联调团队，涵盖技术、业务、测试等多领域专业人员，明确各成员职责与分工。制定详细的联调计划，确定联调的时间节点、范围与目标，将整体联调任务拆解为多个子任务并分配优先级。同时，搭建统一的联调环境，确保硬件资源、网络配置及软件版本与生产环境高度一致，为联调工作提供稳定基础。收集并整理各系统数据字典、接口文档等资料，对联调所需的数据进行预处理，包括数据清洗、格式转换等，保证数据质量符合联调要求，为后续联调工作的顺利开展做好充分准备。

#### 接口功能联调阶段

接口功能联调是数据联调的核心环节。依据接口文档，对各系统间的接口进行逐一测试，验证接口的连接稳定性、数据传输准确性及功能完整性。采用自动化测试工具与手动测试相结合的方式，模拟不同业务场景下的数据交互，检查接口能否正确接收和返回数据，数据格式是否符合约定规范。对于出现问题的接口，及时记录错误信息并定位问题根源，协调相关开发团队进行修复与优化。同时，建立接口联调问题跟踪机制，实时监控问题处理进度，确保每个接口问题都能得到及时解决。在完成单个接口测试后，进行多接口的集成测试，检查接口之间的协同工作能力，保障数据在不同系统间能够顺畅流通。

#### 数据一致性联调阶段

数据一致性联调旨在确保各系统中相关数据在联调过程中的准确性和一致性。选取关键业务数据作为联调对象，如客户信息、交易数据等，对比不同系统中同一数据的值是否一致。通过数据比对工具，自动识别数据差异并生成详细报告。针对数据不一致的情况，深入分析原因，可能是由于数据同步延迟、数据转换错误或数据录入错误等导致。根据分析结果，制定相应的数据修正方案，协调相关系统进行数据调整与同步。在数据修正后，再次进行比对验证，直至各系统间的数据完全一致。建立数据一致性监控机制，在联调过程中持续监测数据变化情况，及时发现并解决潜在的数据一致性问题。

#### 联调总结与优化阶段

联调总结与优化阶段是对整个数据联调工作的全面复盘。组织联调团队召开总结会议，对联调过程中遇到的问题、解决方案及经验教训进行深入交流与分享。整理联调过程中的文档资料，包括测试用例、问题报告、修正方案等，形成完整的数据联调知识库，为后续项目提供参考。根据联调结果，对各系统的性能、稳定性及数据质量进行评估，针对存在的不足之处提出优化建议。协调相关开发团队对系统进行优化改进，如优化接口性能、完善数据同步机制等。制定数据联调的后续维护计划，明确维护周期与责任人，确保数据联调成果能够长期保持，为霍尔果斯“数字链计划”一期项目的顺利上线和稳定运行提供有力保障。

## 数据采集管理

### 数据采集周期

根据数据采集的需要，数据采集周期可分为：

a) 数据一次采集：一次性将所有待采集数据（如一个完整的数据表）全部采集到中心汇聚库；

b) 数据实时采集：采集响应时间要保证实时性、低延迟，可按秒、分进行数据片采集；

c) 数据周期采集：根据数据产生的业务时间进行数据分片，统一形成周期性的数据片进行轮询数据采集，可按每周、每月、每季、每年等时间周期进行数据片采集。

### 数据采集更新机制

数据采集更新机制，主要有全量抽取和增量抽取两种更新机制。

1.全量抽取

全量抽取，宜按照如下要求：

a) 清空中心汇聚库中目标表的数据；

b) 将确定的待采集数据的表或视图原封不动的从数据库中抽取出来，并转换成ETL工具可识别的格式，全量导入到中心汇聚库的目标表。

2.增量抽取

用于抽取自上一轮次抽取后数据库表发生变化的数据。捕获变化的数据可采用的方式有：触发器、时间戳、全表比对、数据版本和日志对比。

（1）触发器方式

触发器方式进行增量抽取，宜按照如下要求：

a) 在要抽取的表中建立基于插入、修改和删除操作的触发器；

b) 源表的数据发生变化，相应的触发器将变化的数据写入临时表；

c) 抽取线程从临时表抽取数据。

（2）时间戳方式

时间戳方式进行增量抽取，宜按照如下要求：

a) 在源表上增加一个时间戳字段；

b) 更新或修改表数据时，修改时间戳字段值；

c) 数据抽取时，通过比较系统时间与时间戳字段值来确定抽取的数据。数据库的时间戳支持自动更新，则时间戳字段值自动更新；数据库不支持时间戳自动更新的，则要求手工更新时间戳字段值。

（3）全表比对方式

全表比对进行增量抽取，逐条比较源表和目标表的记录，将新增和修改的记录读取出来。可采用MD5校验码，宜按照如下要求：

a) 给抽取的表建立一个结构类似的MD5临时表，临时表记录源表主键以及根据所有字段的数据计算出来的MD5校验码；

b) 数据抽取时，对源表和MD5临时表进行MD5校验码的比对，确定源表的数据是新增、修改还是删除，同时更新MD5校验码；

c) 比对结果不同，执行更新操作。若目标表不存在该主键值，执行插入操作；若目标表存在该主键值，而源表不存在，执行删除操作。

（4）数据版本方式

数据版本进行增量抽取，宜按照如下要求：

a) 在表中增加版本号列来存储数据行变化，每次变化都将版本号列的数据增加1；

b) 使用参考表记录每次采集数据时对应的版本；

c) 将参考表与源表的版本号比较来判断需要采集的数据；

d) 采集完后将参考表对应版本号更新为与源表一致的版本号。

（5）日志比对方式

日志比对进行增量抽取，宜按照如下要求：

a)需要资源提供方打开被采集数据库的归档日志；

b)扫描日志文件查看数据库表的变化情况进行实时采集。

# 接口需求

本章节详细规定了系统与用户、外部系统及内部组件之间的交互规范，旨在确保系统界面的易用性、接口调用的安全性以及数据传输的高效性与合规性。

## 用户界面（UI）

政务规范与风格一致性：用户界面设计应严格遵循国家政务UI设计规范，确保整体视觉风格统一、专业、庄重。页面布局应合理清晰，以民生需求为导向，提升政务服务的易用性和亲和力。

响应式与多端适配：页面应采用响应式设计架构，确保在手机、平板、桌面电脑等各类终端设备上均能良好展示与流畅操作，提供一致的用户体验。

无障碍访问设计：系统必须充分考虑无障碍访问需求，全面支持屏幕阅读器等辅助工具，确保视障、老年等特殊群体能够顺畅获取政务信息并办理相关事务。

数据安全底线：在UI交互设计中必须融入安全意识，涉及敏感信息的展示需进行脱敏处理，防止隐私泄露，满足政务系统对信息安全的高标准要求。

## 软件接口（API）

RESTful架构与数据格式：所有对外提供的服务接口应统一采用RESTful架构风格，严格遵循HTTP语义化请求方法（如GET、POST、PUT、DELETE）。接口请求与响应报文统一采用JSON格式，字段命名遵循小驼峰规则，嵌套层级不超过3层，以保证接口的清晰性与可读性。

认证与授权机制：API调用需通过JWT Token进行身份认证，Token的签发与验证应支持OAuth 2.0/OpenID Connect标准协议。系统应建立基于RBAC（角色权限控制）的精细化权限模型，确保接口级权限粒度，拦截非法请求。

报文规范与国密算法：所有通信报文须使用UTF-8编码格式。为保障数据传输安全，签名算法必须采用SM2等国密算法，严禁明文传输敏感数据。

版本控制与兼容性：接口路径需嵌入版本号，采用语义化版本管理。新增功能或重构接口需升级版本号，旧版本接口至少保留6个月的维护过渡期，确保向下兼容，避免破坏性变更。

统一返回结构与错误处理：所有接口需返回标准化的JSON结构，包含状态码（code）、提示信息（msg）、业务数据（data）及分页总数（total）。错误码体系需全局统一，4xx代表客户端异常，5xx代表服务端异常，复杂错误需附带详细原因说明，便于前端排查与国际化展示。

## 通信接口

内网传输与连接管理：系统内部组件间通信应采用HTTPS协议，支持长连接机制以提升传输效率。需明确连接池大小、Keep-Alive超时时间及请求超时阈值（建议默认5秒并支持动态调整），避免资源浪费或请求阻塞。

跨境专线与物理隔离：与境外系统或数据源的通信必须通过独立的物理链路进行，专线带宽不低于50Mbps。该链路需与内网逻辑隔离，确保核心数据跨境传输的低延迟、高可靠性及绝对安全。

数据压缩与传输优化：针对大报文传输，通信接口应支持GZIP或DEFLATE等压缩算法，有效减少网络传输体积。

容错与重试机制：针对网络瞬时异常或超时，通信接口应具备自动重试机制；若服务持续不可用，应支持返回兜底缓存数据，保障系统整体的高可用性。

本章节详细规定了系统的数据架构、数据定义、数据流转及数据安全等方面的要求，旨在确保系统数据的完整性、一致性、准确性及安全性，为后续的系统设计、开发、测试及运维提供统一的数据标准参考。

## 数据模型

系统应建立清晰、规范的核心实体关系图（ER图），以图形化和结构化的方式展示系统的数据架构。

核心实体定义：需明确涵盖用户、组织机构、数据资源、数据服务、审批流程等核心业务实体，并定义各实体的核心属性。

关系与约束：明确定义各实体间的关联关系（如一对一、一对多、多对多），以及相应的主键、外键约束。

索引策略：针对高频查询字段、外键字段及联合查询场景，制定合理的索引策略，以保障系统的数据检索性能。

数据完整性：设定严格的数据完整性约束（包括实体完整性、参照完整性和用户自定义完整性），防止非法或无效数据的产生。

## 数据字典

系统应提供完整且易于维护的数据字典，作为业务人员和技术人员之间的“翻译官”。数据字典需详细列出所有数据库表及字段的技术与业务信息，具体包括：

基础属性：字段名（中英文）、数据类型（如VARCHAR， INT， DATETIME等）、数据长度及精度。

约束与默认值：明确字段是否允许为空（NOT NULL）、唯一性约束、默认值设定及取值范围（枚举值）。

业务语义：提供详尽的字段注释（中文），解释该字段在业务场景中的具体含义、计算逻辑或使用规则。

关系映射：清晰标注字段的主外键关系，说明其关联的父表及父字段。

动态维护能力：对于系统中频繁变动的枚举类数据（如状态、类型等），建议通过数据字典管理模块进行动态维护，以提升系统的可扩展性。

## 数据流转与处理

数据流向：明确描述核心数据在系统各模块间的产生、传输、处理及存储路径。

外部交互：定义系统与外部系统（如第三方API、硬件设备、数据仓库等）交互时的数据格式（如JSON， XML）、传输协议及字段映射规则。

数据转换：说明数据在采集、清洗、加工过程中的转换规则与校验逻辑。

## 数据安全与合规

敏感数据保护：识别系统中的敏感数据（如用户密码、个人隐私信息、财务数据等），并规定相应的加密存储与脱敏展示规则。

访问控制：基于角色或属性定义数据的访问权限，确保用户仅能访问其权限范围内的数据。

审计追踪：记录关键数据的增删改查操作日志，包括操作人、操作时间、操作类型及变更前后数据快照，以满足安全审计需求。

合规性：确保数据的采集、存储和处理符合国家相关法律法规及行业标准（如《数据安全法》、《个人信息保护法》等）。

## 数据生命周期管理

数据备份与恢复：制定明确的数据备份策略（全量/增量备份频率、保留周期）。

数据归档与销毁：针对历史数据或过期数据，制定合理的归档策略以释放主库性能；同时明确数据销毁的流程与标准，确保被销毁的数据无法被恢复。
